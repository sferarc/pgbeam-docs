Read-only enforcement keeps an agent off your data by refusing every write. That
is the right default for most agents. It is also too restrictive when the agent's
job _is_ to write: running a migration, backfilling a column, or testing a
generated `UPDATE` before you trust it against production.

Sandbox writes are the safe-write counterpart to read-only enforcement. Instead
of blocking the write or letting it touch production, PgBeam hands the agent an
instant, isolated branch: a throwaway copy of your database. The agent writes
against the branch as if it were production. When the agent is done, you discard
the branch. Production is never touched.

## What it does

A sandbox is an ephemeral, writable branch of a database, scoped to an agent
credential.

- **Isolated**: writes land on the branch, never on production.
- **Instant**: the branch spins up in seconds, ready for the agent to use.
- **Throwaway**: discard the branch when the session ends. Nothing merges back
  unless you explicitly promote it.
- **Ephemeral**: an idle branch costs nothing to keep around, and a discarded
  branch is gone.

The agent connects the same way it connects today: a scoped PgBeam credential or
the hosted MCP endpoint. The difference is the target. A sandbox credential
routes the agent's session to a fresh branch instead of the production upstream.

## How you'll use it

<Callout type="info">
  The workflow below describes the planned experience. Commands and field names
  are not final.
</Callout>

1. Create a sandbox policy on an agent credential, marking it write-capable
   against a branch instead of production.
2. The agent opens a session. PgBeam provisions a fresh branch from the
   database's current state and pins the session to it.
3. The agent writes freely: `INSERT`, `UPDATE`, `DELETE`, even DDL, all against
   the branch.
4. You inspect what the branch changed in the dashboard: which rows moved, which
   statements ran, and the full audit trail for the session.
5. You discard the branch, or promote its changes to production after review.

## How it works

When an agent opens a session under a sandbox policy, PgBeam provisions an
isolated branch of the target database. The branch starts from production's
current state and spins up in seconds.

The branch is a real Postgres endpoint. The agent's session connects to it
through the same wire-protocol proxy that enforces every other policy, so audit
capture, query budgets, and masking still apply on the branch. Read-only
enforcement is relaxed for the branch and only the branch: the agent can write,
because there is nothing on the branch worth protecting.

Branches are ephemeral by design. An idle branch costs nothing to keep, and a
discarded branch is torn down. Promotion to production is an explicit,
operator-driven step, never automatic. If you never promote, the agent's writes
disappear with the branch.

This keeps the core guarantee intact: an agent with a sandbox credential cannot
change production data. The worst case is a wasted branch.
